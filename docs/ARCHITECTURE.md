# Architecture

The endpoint has a durable SQLite spool and a TLS 1.2-or-newer client. Synthetic event creation and explicit single-record `event.v1` import both pass through the active policy gate. Imported records are schema-allowlisted, root-scoped, and normalized; target paths are transformed with a store-local HMAC-SHA-256 key and never enter the queue in raw form. The agent hashes the payload, assigns a durable sequence, and stores it before networking. It sends bounded batches to a loopback mTLS endpoint and removes only IDs explicitly accepted or identified as duplicates by the authenticated server. Queue size and byte quotas stop unbounded growth; retry uses bounded exponential delay with jitter.

The reference server verifies each client-certificate chain and separates agent and operator common-name allowlists. Event ingestion requires an agent identity and commits event IDs under a unique agent/event key before acknowledgements. Policy publication requires an operator identity plus a bearer token; the server validates the restricted tenant policy, signs its exact bytes with Ed25519, and stores a monotonic revision. Agent fetch supports an ETag/304 unchanged response. The database contains event metadata/hashes and the current signed policy.

The agent and server each have a bounded JSON parser that enforces JSON number/whitespace grammar, duplicate-key rejection, maximum nesting, and a 1 MiB text cap. Separate parser tests guard both copies. The custom HTTP/1.1 subset limits headers to 16 KiB and bodies to 1 MiB, requires unambiguous Content-Length framing and JSON Content-Type for event batches, and requires HTTP 200 for event acknowledgements. Policy fetch accepts HTTP 200/304. It rejects Transfer-Encoding and duplicate framing/authentication headers, applies a 5 second per-I/O timeout, and enforces a configurable 10 second absolute TLS handshake deadline plus a separate HTTP header/body receive deadline after TLS peer and CN authorization. The HTTP deadline excludes route handling. Both timeouts are configurable from 100 to 60,000 ms. This is a deliberately limited lab implementation, not a general HTTP stack.

Policies are separately signed with Ed25519 over exact document bytes. Agent validation rejects unknown top-level/settings fields and unsafe actions, checks issued/expiry timestamps, tenant/root scope, and monotonic revision, then commits last-good state and audit in one SQLite transaction. When collection is enabled, it first prepares a complete candidate inotify watch tree; failure prevents the policy transaction from committing. During long-running reload, a new collector owns a separate inotify FD and watch map until required roots are ready. The runtime swaps collectors only after preparation, so failure leaves its current in-memory policy and watches active. TLS authentication does not replace detached policy signature verification. The collector observes directory-entry, close-write, attribute, delete, and move notifications, never opens file contents, and routes events through the same event.v1 allowlist, path HMAC, sequence, and SQLite queue used by explicit imports. It traverses directories using no-follow dirfds, watches the opened directory through `/proc/self/fd`, prunes cross-device subtrees, caps watches, and reports loss/overflow as degraded coverage. `telemetry_enabled`, `sample_rate`, expiry, and root changes are reread during the event loop. A positive `--interval-seconds` enables the long-running collector. These additions have not been built or verified; they do not create a content baseline or claim complete file-integrity coverage. Filesystem changes after preflight and behavior across process restart still need technical verification.

A C transport probe is limited to loopback TCP connectivity; TLS is implemented only in the C++ agent/server.


## Agent registry and certificate lifecycle

A trusted client certificate is mapped to its UUID CN and a unique SHA-256 fingerprint in SQLite. The optional `--agents` file inserts bootstrap identities; a first trusted certificate is pinned only for a seeded identity with no prior certificate history. Operator mTLS plus a separate bearer token protects explicit enrollment, pending-certificate rotation, revocation, and re-enrollment routes. The pending pin becomes current on first authenticated use; revocation disables the registry row and blocks both current and pending certificates. Agent status and heartbeat read/update the registry. These new server routes have not been built or verified after implementation.
